# ADR-0006: Evidence ledger and report grounding

Status: accepted (2026-10-17)

## Context

An LLM can write a convincing report that no tool result supports. The assignment asks for observable tool calls, reliable structured output and guardrails; a marketer will act on the conclusion (pause a campaign, change bids), so unsupported certainty is the failure that matters most. Every runtime (built-in, deterministic, IDE agent, OpenClaw) must be held to the same standard.

## Options considered

| Option | Verdict |
|---|---|
| Trust the model's report, validate only the JSON shape | Rejected: shape says nothing about truth. |
| A second model grading the first | Rejected: adds cost and a second source of error; not deterministic, cannot be unit-tested. |
| **A ledger of everything that happened plus deterministic grounding rules checked on submit** | **Chosen.** |

## Decision

**Ledger (PostgreSQL).** One investigation row with an explicit state machine (`QUEUED`, `RUNNING`, `COMPLETED`, `FAILED`, `CANCELLED`, `INTERRUPTED`; transitions are `UPDATE ... WHERE status = <expected>`, terminal states are immutable). Append-only events with a per-investigation sequence number, tool executions (each call is `REQUESTED`, `REJECTED`, `RUNNING`, `SUCCEEDED` or `FAILED`, with attempt, duration and error code), and numbered evidence (`E1`, `E2`, ...) whose statements are generated by code from the tool's numbers, never by the model. What is stored: tool inputs and outputs, the one-line reason the agent gave for each call, model-turn metadata. What is never stored: hidden reasoning. The UI polls only persisted events, so nothing on screen is a spinner pretending to be a step.

**One path for tools.** `ToolExecutor.execute` validates the arguments against the zod schema, checks the tool belongs to the investigation's mode, enforces budgets, de-duplicates by `(investigation, callerRef)`, applies a timeout, retries transient failures once and records every attempt. Third-party text (page content, change-log notes) is sanitised and returned inside an `untrustedContent` envelope with a fixed notice; injection heuristics add signals and a `guardrail.triggered` event.

**Grounding on submit.** `ReportService.submit` parses the report with the zod schema and then applies rules in `apps/api/src/reports/grounding.ts`: every cited evidence id exists; every observation cites evidence; `high` confidence needs a supported hypothesis, at least two supporting items with one direct, and nothing contradicting; `cause_identified` needs a supported high-confidence hypothesis and (demo) a significant period comparison; a significant drop cannot be `no_issue_found`; a non-significant change can only be `inconclusive` or `no_issue_found`; a failed tool caps confidence in the categories it informs; URL reports use URL categories, cannot claim a conversion cause and must carry the scope statement; severity must match the rubric. A rejected report returns machine-readable `{path, rule, message}` errors; three attempts in total, then the run ends `FAILED / REPORT_INVALID`. Key metrics are attached by the server from tool evidence, not copied from model text.

## Trade-offs

- The rules are conservative. A correct but unusual conclusion can be rejected and cost the agent an attempt; the error says which rule fired so it can fix it.
- Evidence statements are templated, so they read less fluently than model prose.
- The rules check support, not truth: if a tool computes a wrong number, the report is "grounded" in it. Tool maths therefore has its own unit tests.

## How verified

Each rule has a unit test; `ReportService` and `ToolExecutor` have integration tests; a scripted "compromised" model (unknown tool, a tool of the other mode, an ungrounded "everything is fine" report) is rejected and logged. The end-to-end tests assert persisted events, evidence and report for every scenario. Two real agents (Claude Code, Codex) had their reports validated by this code ([verification.md](../verification.md)).
